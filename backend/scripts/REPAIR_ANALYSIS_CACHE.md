# Analysis-cache repair: deployment & rollback (g-repair-drill-cache)

Companion to `precompute_openings.py`. The precompute **regenerates**
authoritative opening rows; `repair_analysis_cache.py` **invalidates** the
legacy/contaminated rows the write guard would reject today, so they can no
longer feed the eval-delta / win-chance fallbacks that drive drill pass/fail,
regular-game classification/recording, and SRS grading.

See the [analysis evidence contract](../../docs/architecture/analysis-evidence.md)
for the trust and degradation boundary, and
[`app/analysis_cache_audit.py`](../app/analysis_cache_audit.py) for the pure,
unit-tested category classifier.

## Preconditions — DO NOT skip

Run **only** after, in order:

1. Quality metadata + comparator deployed (`g-guard-cache-writes`) — the write
   guard must be live, otherwise newly-deleted rows can be re-created
   contaminated.
2. Canonical precompute deployed and run to completion
   (`precompute_openings.py`), so the authoritative rows that replace legacy
   coverage exist before anything is deleted.

Regenerating or invalidating before write protection is active is unsafe.

## Procedure

All commands from `backend/` with the venv active
(`source .venv/bin/activate`). Default DB URL is the local Postgres; pass
`--database-url` for production.

**Pick the scope once and keep it consistent across all three steps.** The
`--include-legacy-null` flag changes *which* rows count as invalidation-eligible,
so audit/apply/verify must all be run with the SAME flag — otherwise `--apply`
or `--verify` evaluate a different set than you reviewed. The procedure below
includes legacy cleanup; drop `--include-legacy-null` from every line to do the
default (contaminated-only) repair instead.

```bash
# 1. AUDIT (non-destructive). Inspect the per-category counts + JSON report.
python scripts/repair_analysis_cache.py --database-url "$PROD_URL" --include-legacy-null
cat repair_analysis_cache_report.json

# 2. APPLY once the audit looks right. Bounded, separately-committed, resumable.
python scripts/repair_analysis_cache.py --database-url "$PROD_URL" --include-legacy-null --apply

# 3. VERIFY — exits non-zero if any invalidation-eligible row remains.
python scripts/repair_analysis_cache.py --database-url "$PROD_URL" --include-legacy-null --verify
echo "exit: $?"   # 0 == clean
```

`--apply` re-scans after deleting and records `deleted` +
`post_invalidate_remaining` in the report. The operation is idempotent: an
interrupted `--apply` leaves a consistent table, and re-running deletes whatever
still qualifies.

## What it deletes

The classifier is anchored on the write guard's own `incoming_is_valid` gate — a
row is invalidation material iff the guard would reject it as a write today.

- **By default:** `contaminated_profile_claim` only — rows carrying a non-null
  `analysis_profile_id` that fail the guard (unverifiable identity or evidence
  that fails its declared contract).
- **With `--include-legacy-null`:** additionally `legacy_invalid` — profile-less
  rows the guard also rejects (null or unsatisfied evidence contract, including
  key-only placeholders).

It never deletes guard-accepted rows: `canonical_trusted`, `canonical_retired`,
`non_auth_valid`, or `legacy_valid` (profile-less rows with a satisfied
contract). Profile-less rows are otherwise reclaimed for ECO coverage by a re-run
authoritative precompute (dominance REPLACE), not by deletion.

`--apply` re-classifies every candidate under a row lock inside the deletion
transaction, so a row an overlapping precompute repaired in place (same id, now
canonical) is re-evaluated and spared.

## Rollback

Deletion is destructive and has no in-table undo. Mitigations:

- **Snapshot first.** Take a DB snapshot / `pg_dump` of `analysis_cache`
  immediately before `--apply`. Restore from it to undo.
- **Re-derivable data.** Every deleted row is, by definition, one the system
  treats as untrusted; canonical coverage is regenerated by re-running
  `precompute_openings.py`, and `game`/upload rows are re-created on the next
  session that revisits the position. So the practical recovery for an
  over-aggressive run is: restore the snapshot, or simply re-run the precompute
  for canonical positions.
- **Staged rollout.** Run the audit on production first and review
  `repair_analysis_cache_report.json`; only `--apply` when the
  `contaminated_profile_claim` / `legacy_invalid` counts match expectations.

## Monitoring

The run logs per-category metrics (`analysis_cache audit: N rows total`, then one
line per category) and the number selected for invalidation. After repair,
confirm downstream stability: repeated drills at strict/standard/lenient/custom
thresholds, regular-game classification + first-auto-record, and SRS pass/fail
should all be stable, and live result / `session_moves` / cache lookup /
post-game display should agree.
